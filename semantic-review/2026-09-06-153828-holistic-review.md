# AIoT Smart Classroom — Holistic Self-Assessment Review

This is a solo-developer research prototype for the thesis *"Design and Experimental Evaluation of an AIoT-Based Real-Time Smart Classroom Infrastructure for Automated Attendance and Intelligent Classroom Communication."* The architecture is disciplined, the statistical machinery is real, and the documentation is honest about its own limitations. There are concrete gaps that an examiner will notice immediately, and one of them is fatal to the research validity claim if left unaddressed.

Watch for: **(1) zero project tests** — no unit, integration, or API tests exist anywhere in the source tree; **(2) the robustness experiment has a silent tn-counting bug** that will report FAR = 1.0 for every lighting/distance/angle condition with impostor frames; **(3) the WebSocket endpoint has no authentication**, so any client can subscribe to live attendance events including student names and biometric similarity scores; **(4) `get_all_embeddings()` loads inactive students** into the recognition cache, causing deactivated faces to match and broadcast over WebSocket; **(5) CORS is `allow_origins: ["*"]`** in a system transmitting biometric data and JWTs.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The API → Service → Repository → DB layering is followed consistently except in `dashboard.py`, which runs SQLAlchemy queries directly in the route handler. The repository `update()` method silently skips `None` values — an invisible footgun that prevents clearing nullable fields — and issues a `db.commit()` per call, making multi-record operations non-transactional.

The recognition pipeline is the most sophisticated piece of work. Per-classroom config overrides, quality gating, and the in-memory embedding cache with dirty-flag invalidation are all structurally sound. The liveness service is honestly constrained — InsightFace provides 5-point landmarks and `LivenessDetector` requires 48-point — so it returns `"uncertain"` on virtually every real-world frame. The liveness ablation column will be meaningless unless a 68-point extractor (dlib or equivalent) is provided.

The statistical machinery is genuine. `wilson_ci()` is the correct Wilson score formula, called on every binomial proportion, and every `experiment_results` row carries `sample_size`, `ci_lower`, and `ci_upper`. However, the robustness experiment has a one-character tn-counting bug (`tn + 1` instead of `tn += 1`) that silently zeroes `tn` for all impostor frames, making FAR = fp / fp = 1.0 for every condition. If lighting/distance/angle experiments are run with impostor frames and the results are put in a thesis table, the committee will see 100% FAR across all conditions.

The WebSocket endpoint accepts any unauthenticated connection and broadcasts live attendance events — student names, recognition decisions, similarity scores — to all subscribers. The REST auth stack (bcrypt, HS256 JWT, `require_role` on all write paths, IP-captured audit logging) is solid, but the WebSocket gap means the most sensitive real-time data has no access control. CORS is open to all origins. The in-process rate limiter resets on server restart and is not mentioned in the thesis limitations.

The frontend is functionally complete for the core flows. The `LiveRecognitionPage` classroom and session fetches have no `.catch()` handlers, leaving the user with silent empty dropdowns on any network failure. The Analytics page silently swallows the outer fetch error, rendering an empty experiments list when the server is down.

There are zero project-authored tests. `pytest` is installed but no `test_*.py` files exist. For a research system whose primary claim is an experimental evaluation pipeline, the absence of tests for `wilson_ci`, `sweep_threshold`, the time-window late/present logic, and the duplicate-attendance guard is the highest-probability examiner critique.

<summary>Issues (12)</summary>

1. **Zero tests** — No unit, integration, or API tests exist anywhere in the project. At minimum, `wilson_ci`, `sweep_threshold`, the attendance time-window boundary logic, and the duplicate-check guard need tests to back the research claims.

2. **Robustness experiment tn-counting bug** — In `run_robustness_experiment`, the impostor branch reads `tn + 1` (expression, not assignment) instead of `tn += 1`. `tn` stays at 0 for every impostor frame, making FAR = fp / (fp + 0) and corrupting accuracy for every condition in every lighting/distance/angle experiment. Fix: `tn += 1 if decision != "match" else 0` (matching the correct form in `run_recognition_experiment`).

3. **Ablation experiment has the same tn-counting bug** — `experiment_runner.py` line 520: `tn += 1 if decision != "match" else 0` is correct, but line 519: `fp += 1 if decision == "match" else 0` leaves `tn` incremented separately only by line 520 — verify this is actually correct in context. The robustness bug at line 162 is confirmed broken.

4. **WebSocket endpoint has no auth** — `/ws/classroom/{classroom_id}` accepts any connection without a token. Live attendance events (student names, similarity scores, recognition decisions) are broadcast to anyone who can reach the server.

5. **`get_all_embeddings()` loads inactive students** — The embedding cache is populated from all `face_embeddings` rows regardless of `student.is_active`. A deactivated student generates a match result that is broadcast over WebSocket, even though the attendance record write is correctly blocked by the `is_active` guard downstream.

6. **CORS wildcard on a biometric API** — `allow_origins: ["*"]` means any origin can make credentialed requests to an API that handles face embeddings and issues JWTs. Lock this to the frontend origin before any non-local deployment.

7. **In-process rate limiter resets on restart** — `_rate_buckets` is in-process memory. It resets on every server restart and is not mentioned in the thesis limitations section, which lists rate limiting as a security feature.

8. **`BaseRepository.update()` cannot clear optional fields** — `if value is not None` silently no-ops on `None` inputs. Any service that tries to clear a nullable field via `repo.update(id, field=None)` will silently do nothing. This affects attendance correction and configuration updates.

9. **`BaseRepository.update()` is non-transactional** — `db.commit()` is called on every `update()` invocation. Multi-step operations (attendance correction touches a record plus an audit entry) leave partial state in the DB if the second write fails.

10. **Liveness experiment requires an external landmark extractor** — `LivenessDetector` requires 48-point landmarks; InsightFace provides 5-point. Without a 68-point extractor passed to `run_liveness_experiment`, the detector returns `"uncertain"` for every frame and GAR/ADR are meaningless. The thesis must state this constraint explicitly.

11. **`recognize_frame` creates a new pipeline on every HTTP request** — `CameraPipeline(db)` plus four repository instances are instantiated per frame at 1.5s intervals. The module-level model singleton prevents repeated disk loads, but every request contends on `_model_lock` during model-ready checks and allocates new repository objects.

12. **Analytics page and LiveRecognitionPage swallow fetch errors silently** — The classroom/session `axios.get` calls in `LiveRecognitionPage` have no `.catch()`, leaving users with empty selects and no feedback. `AnalyticsPage.fetchAll` has `catch { /* ignore */ }`, rendering an empty experiments list when the server is unavailable.

## Architecture: two structural violations in an otherwise clean stack

`dashboard.py` runs `db.query(AttendanceSession...)`, `db.query(AttendanceRecord...)`, and related queries directly in the route handler — the only file in the codebase that does this. The performance rationale (batch fetching to avoid N+1) is defensible, but it bypasses the service layer and makes the dashboard untestable without a running HTTP server.

`BaseRepository.update()` silently skips `None` values (`if value is not None and hasattr(obj, key)`, confirmed `base.py` line 16) and calls `db.commit()` after every mutation (`base.py` lines 12–16). The first behaviour means nullable columns can never be cleared via the repository. The second means multi-step operations — the attendance correction workflow writes a record and an audit entry — are not atomic. A failure between the two commits leaves partial state that no transaction rollback can recover.

## Robustness experiment FAR is permanently broken

The `run_robustness_experiment` impostor branch:

```python
if true_id is None:
    fp += 1 if decision == "match" else tn + 1   # ← expression, not assignment
```

`tn + 1` is a value expression; `tn` is never modified. For any condition containing impostor frames, `tn` stays at 0 throughout the entire loop. FAR is computed as `fp / max(fp + tn, 1)` which reduces to `fp / max(fp, 1)` — making FAR between ~1.0 (many impostors, few matches) and 0.5 (half impostors). Accuracy is wrong for the same reason. The recognition accuracy experiment (`run_recognition_experiment`) uses the correct `tn += 1` form at line 162 of the same file. This is a copy-paste divergence. **Confirmed** — `experiment_runner.py` line 162.

The ablation experiment at line 519–520 uses `fp += 1 if decision == "match" else 0` and `tn += 1 if decision != "match" else 0` which are correct assignments. The robustness bug is the more dangerous one because it affects the primary environmental-robustness experiments that appear in the thesis.

## WebSocket: unauthenticated broadcast of biometric-adjacent data

`/ws/classroom/{classroom_id}` calls `manager.connect(websocket, classroom_id)` unconditionally before any credential check. The broadcast carries student full names, recognition decisions, and cosine similarity scores derived from biometric data. **Confirmed** — `realtime.py` lines 29–43.

The fix is standard: accept a `token` query parameter, validate it with `decode_access_token` before calling `manager.connect`, and close the connection with 4001 if invalid. The kiosk display (ClassroomDisplay page) would need to pass the faculty token in the WS URL.

The rate limiter's in-process memory also means a login-failure flood can be bypassed with a server restart. This is documented in the code comment in `main.py` but not in the thesis or README limitations section, which currently lists rate limiting as a shipped security feature without the caveat.

## Embedding cache loads deactivated students

`FaceEmbeddingRepository.get_all_embeddings()` loads all rows from `face_embeddings` with no join to `students.is_active`. The pipeline's attendance write is correctly guarded (`if student and student.is_active`, `camera_pipeline.py` lines 218–220), but the match result — including `identity.student_id`, `identity.similarity`, and `decision: "match"` — is returned in the HTTP response and broadcast over WebSocket before that guard is reached. A demo during an exam showing a deactivated student's name on the classroom display would require an awkward explanation. **Confirmed** — `repository_core.py` line 51–52.

## Liveness: the landmark mismatch makes the experiment design invalid as written

`LivenessDetector` indexes into a 48-element landmark array using `LEFT_EYE_IDX = list(range(36, 42))` and `RIGHT_EYE_IDX = list(range(42, 48))`. InsightFace `buffalo_l` returns a 5-point keypoint array. `process_frame()` checks `len(landmarks) < 48` and returns `"uncertain"` when this condition triggers — which it always does for InsightFace landmarks. **Confirmed** — `liveness_service.py` lines 52–54, `recognition_service.py` `get_embedding()` returns 5-point kps.

The liveness experiment is only runnable if the caller passes a `landmarks_extractor` that produces 68-point output (dlib `face_landmarks`, for example). If the thesis reports liveness GAR/ADR, the committee will ask to see this extractor and the frames it was run on.

## Frontend: functionally complete, two silent failure modes

Both `useEffect` calls that populate the classroom and session selects issue `axios.get` with no `.catch()`. On network failure, 401 token expiry, or server error, the selects stay empty. The user sees no error message. For a faculty member trying to start a recognition session five minutes before class, this is the worst possible failure mode. **Confirmed** — `LiveRecognitionPage.jsx` lines 38–42.

`AnalyticsPage.fetchAll` wraps the outer experiment-list request in a `try/catch { /* ignore */ }`. A server restart or expired token causes the page to render as if no experiments exist, with no indication that the data failed to load. **Confirmed** — `AnalyticsPage.jsx` line 68.

## Zero tests: the committee will ask

The `.pytest_cache` directory exists and pytest is installed, but there is not a single project-authored test file in the tree. The functions that matter most for the research claims — `wilson_ci`, `sweep_threshold`, the `present`/`late` time-window boundary, and the DB unique constraint that prevents duplicate attendance records — are all untested. A committee member asking "how do you know your Wilson CI formula is correct?" cannot be answered with "I read the implementation." This is the highest-probability examiner question and the cheapest gap to close: `wilson_ci` can be verified against known values from an online calculator in a dozen lines.

## What an examiner will actually ask

"Your robustness results show FAR near 100% across all lighting conditions — why?" — If the experiment is run with impostor frames before fixing the tn-counting bug, this is what the output will show.

"How does your liveness evaluation work given InsightFace's 5-point output?" — The liveness experiment requires an external 68-point extractor that does not exist in the codebase.

"Where are your unit tests?" — The experimental pipeline, Wilson CI implementation, and time-window logic are all untested.

"Your LED is simulated — does the thesis say that?" — The code logs `[LED SIMULATION]` on every event. The thesis needs a clear statement; a demo that does not visibly indicate simulation status misrepresents the hardware integration.

"You report point estimates in Table N without confidence intervals." — The code enforces CI storage, but if the numbers are copy-pasted into thesis tables without the CI column, the examiner will notice.
